# Android packaging decision — مودي وعبودي on Google Play

Status: built and verified in a sandbox up to a **signed AAB + debug APK** (see "What was verified"). **Not run on a device or emulator** — nobody has seen the app launch yet. Do the internal-test step in `RELEASE_CHECKLIST.md` before trusting anything below.

## 1. Capacitor wrapper, not a Trusted Web Activity

| | Capacitor (chosen) | TWA (Bubblewrap / PWABuilder) |
|---|---|---|
| Web assets | **Bundled inside the AAB.** Works offline from the first launch, no domain involved. | Loaded from your website; offline only through the service worker cache. |
| Domain verification | None. | Needs `/.well-known/assetlinks.json` at the **origin root** (`https://host/.well-known/…`). |
| Your hosting | `https://<user>.github.io/hatem-games-hub/moody/` is a *project page*: the origin is `https://<user>.github.io`, and you cannot put a file at that origin's `/.well-known/` from a project repo. A TWA there cannot pass verification (it would open as a Custom Tab with the URL bar). |  |
| Workaround for TWA | — | A **user-site repo** named `<user>.github.io` (serves the origin root), or your own domain. Possible, but then the app depends on the website being up, and 100–150 MB of voice still has to be cached on first run. |
| Billing | Works through a native plugin (section 3). | Needs the Digital Goods API + Payment Request, only in Chrome-based TWAs and still picky. The game's `digitalgoods` provider exists for that route. |
| Store review | Normal app with bundled content. | A thin web shell is sometimes questioned; offline content is a plus. |
| Cost of Capacitor | ~6 MB of wrapper, a JDK/Android SDK toolchain, and **you** own WebView quirks. | |

Decision: Capacitor. If you later own a domain, a TWA is a cheaper-to-maintain second channel, not a replacement.

## 2. What is in `android/`

```
android/capacitor.config.ts      appId PLACEHOLDER com.example.moodyadventures, https scheme, no server.url, allowNavigation []
android/version.json             versionName / versionCode (CI overrides with run number)
android/bridge/native_shell.js   injected first in <head>: no service worker, hides the web fullscreen toggle and the hub link ("../"), BACK button
android/bridge/billing_capacitor.js   window.MoodyBillingCapacitor (Play Billing through cordova-plugin-purchase)
android/bridge/test_billing.js   node test of the bridge against a mock plugin (run: node bridge/test_billing.js)
android/scripts/make_www.js      play_dist -> www (+ policy lint + size report + optional voice split)
android/scripts/build.sh         one command: www -> cap sync -> gradle (debug APK / release AAB)
android/scripts/set_app_id.js    sets the package name (one place)
android/scripts/make_icons.py    adaptive + legacy + monochrome icons and splash icon from the cartoon avatars
android/android/                 the native project (generated by `npx cap add android`, then edited)
android/android/voice_pack/      Play Asset Delivery install-time pack scaffold (off unless -PvoicePack=true)
.github/workflows/android.yml    CI (written, not run — see below)
```
Flow: `node tools/play/build.js play_dist` (other agent) → `make_www.js` copies it into `www/` and injects the two bridge scripts → `cap sync` → Gradle. Nothing in the game's source is edited.

`make_www.js` also **lints the build for things Google will reject**: unlock-code/paywall leftovers (`paywall.js`, "كود الاشتراك"), payment-channel links, absolute-URL network calls, analytics/ads SDK names, `../` references outside the web root. Errors stop the build.

## 3. Billing: which plugin

Hard requirement: digital content unlocked inside a Play app must be sold through **Google Play Billing**. No codes, no "write us by e-mail", no payment links in the Play build (Payments policy). The hub's existing `paywall.js` (activation codes by e-mail) must not ship in this edition.

| Option | License / cost | Notes (verified = I read the package; otherwise from memory) |
|---|---|---|
| **`cordova-plugin-purchase` 13.x (CdvPurchase)** — chosen | MIT, free, no account | verified: installs into Capacitor via `cap sync`, pulls Play Billing Library 9.0.0, adds only `com.android.vending.BILLING`, no network of its own, no analytics. Works **without any server**. Weakness: no server-side receipt validation unless you add a validator; no expiry date from Google without one. |
| RevenueCat `@revenuecat/purchases-capacitor` 13.x | MIT SDK; service free until a revenue threshold then a % of tracked revenue (check current pricing) | Better entitlements, server-side validation, dashboards. But it is a **third-party SDK that talks to RevenueCat's servers** (app-user id, device info). In a Families app that means declaring it in Data safety, relying on its Families-compliance statements, and changing the "no third-party SDKs" privacy line. Reasonable later if you need real validation; wrong default for a no-data children's app. |
| `@capgo/native-purchases` 8.x | MPL-2.0 | Newer, smaller Capacitor-native plugin around StoreKit 2/BillingClient. Not evaluated in depth. Viable alternative. |
| Own ~300-line Capacitor plugin around `BillingClient` | yours | Full control, you maintain it against every Billing Library deprecation. |

**Chosen: CdvPurchase**, behind the small bridge `android/bridge/billing_capacitor.js`, so the plugin can be swapped without touching the game (contract: `BILLING_CONTRACT.md`).

How it is wired:
- Two subscriptions, one base plan each: `moody_premium_monthly`, `moody_premium_yearly` (you may instead create one subscription with two base plans; then pass the base-plan offer id — the bridge supports `offerId`).
- On start the bridge emits the cached entitlement at once (offline child is not locked out), then asks Google Play (`receiptsReady`) and emits the authoritative answer. Purchases are acknowledged (`finish()`), because Play refunds unacknowledged purchases after 3 days.
- **Honest limit:** without a validator, "entitled" means "Google Play Services on this device says the subscription is active". Expiry dates are usually unknown (`expiry: null`). That is acceptable for a kids' content unlock, not tamper-proof on a rooted phone. Upgrade path: add a validator (RevenueCat or your own Cloud Function using the Play Developer API) — only then does the privacy policy change.
- The game must show the **parental gate before** calling `purchase()` and before `manage()`.
- Fees (verify): Play keeps 15% of subscription revenue; some countries add VAT handled by Google.

## 5. Permissions (all of them)

| Permission | Why | Could it go? |
|---|---|---|
| `INTERNET` | Capacitor's WebView plumbing and Play Billing round-trips. The game itself makes no network calls. | Probably removable (`tools:node="remove"`; Play Billing talks to the Play Store app over IPC) but **unverified on a device** — if you try it, test a real purchase first. |
| `com.android.vending.BILLING` | subscriptions | no |
| `ACCESS_NETWORK_STATE` | added by a library (billing/play-services side) | merged; harmless |
| `…DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | AndroidX internal, signature-protected | no |
| `AD_ID` | **removed explicitly** (`tools:node="remove"`): a Families app must not hold the advertising id | — |
Not requested: camera, microphone, location, contacts, storage, notifications. Wake Lock is the web API (no permission) plus `FLAG_KEEP_SCREEN_ON`.

## 6. Native behaviour choices

- **Orientation:** `sensorLandscape` (both landscape directions).
- **Immersive:** `MainActivity` hides system bars (swipe shows them transiently), re-applies on focus/resume.
- **Keep screen on:** `FLAG_KEEP_SCREEN_ON` for the whole foreground session (simple and reliable; the game's own Wake Lock during missions still runs). Trade-off: screen stays on in menus. If you prefer, delete that one line in `MainActivity.java` and rely on the web Wake Lock only.
- **Back button:** `native_shell.js` listens to Capacitor `App` `backButton`. Order: (a) `Moody.onBack()` if the game defines it and returns `true`; (b) otherwise it dispatches an `Escape` keydown — the game already maps Escape to *pause* in a mission and *close* in modals (`ctx.js`, `ui.js`); a handled event calls `preventDefault`; (c) otherwise "press back again to exit" (2 s), then `App.exitApp()`. Suggestion for the game owner: add `Moody.onBack = () => {…}` for exact behaviour (e.g. "back from map → title").
- **Service worker disabled** in the app (assets are local; updates come through Play; a SW would duplicate ~150 MB into the cache). The web fullscreen toggle is hidden.
- **Backups off:** `allowBackup=false`, `dataExtractionRules` exclude everything, no `fullBackupContent`. Progress stays on the device.
- **Network:** cleartext disabled, system CAs only, `allowNavigation: []`, no `server.url`.
- **R8/ProGuard:** **off by default.** Java code is tiny; Cordova/Capacitor plugins are reflection-loaded; I could not test a minified build on a device. Switch on with `-PminifyRelease=true` (`proguard-rules.pro` has keep rules for Capacitor, Cordova and the purchase plugin) after testing. Upload the generated `mapping.txt` to Play if you do.
- **Icons:** adaptive icon (gradient background + two avatar circles inside the 66 dp safe zone), legacy square/round, Android 13 monochrome layer, splash icon. All from the game's own cartoon avatars (no photos). `python3 scripts/make_icons.py`.
- **Versioning:** `version.json`; override with `VERSION_NAME`/`VERSION_CODE`. Every upload needs a higher `versionCode`.
- **Package name:** set once with `node scripts/set_app_id.js com.yourname.moodyadventures`. Release builds **refuse** `com.example.*`. The Java namespace is `moody.wrapper` and never changes.

## 7. Size and Play Asset Delivery

Limits as I know them (verify in Play Console → Release → App bundle explorer / "Size" docs): base module ≤ **200 MB** compressed download; install-time asset packs ≤ **1 GB** in total; an AAB upload ≤ **2 GB**; app total ≤ **4 GB** across all delivery types. MP3/JPG/PNG are already compressed, so "size on disk" ≈ "download size".

- Voice is ~100–150 MB. Together with code that is **under** 200 MB but close; with more voice clips or the family variants it will not be.
- `make_www.js` warns above 170 MB (`--max-base-mb`).
- **Split:** `node scripts/make_www.js --src play_dist --split-voice` moves `assets/voice` into `android/android/voice_pack/…/assets/public/assets/voice`; Gradle includes the module only with `-PvoicePack=true` (`build.sh … --split-voice`, or the workflow input). Delivery is `install-time`: the files are installed with the app and are read through the same `AssetManager` path, so Capacitor serves `https://localhost/assets/voice/<hash>.mp3` unchanged — **no Play Core code, no JS changes**. Verified: the AAB contains `voice_pack/assets/public/assets/voice/*.mp3`, base has none.
- The **debug APK does not contain asset packs** — build debug without `--split-voice` to hear voices when sideloading. To test the split on a device use bundletool (`build-apks --local-testing`) or the Play internal track.
- Install-time packs raise nothing for the user (single install); fast-follow/on-demand would need Play Core code in the game — not implemented.

## 8. What was verified here

Done in the sandbox (JDK 21, Gradle 8.14.3, Android SDK 36 downloaded through the proxy): `npm install`, `cap add android`, `cap sync`, **`assembleDebug` OK**, **`bundleRelease` OK** signed with a throw-away key (`jarsigner -verify` passed), with and without the voice pack; the placeholder-id guard fails the release as intended; `aapt2 dump` shows target 36, `allowBackup=false`, landscape, only the permissions listed above; `node bridge/test_billing.js` passes (mock plugin); `native_shell.js` exercised in headless Chromium against the bundled `www/` with a fake `Capacitor.Plugins.App`: service worker rejected, hub link hidden, back → toast → exit on a root screen, back in a mission opens the pause window and a second back closes it. The web build used for these tests was the current `moody/` folder with a few dummy mp3 files — the real Play edition did not exist yet.

**Not verified:** launching the APK itself, the WebView actually loading the game, audio Range requests, Wake Lock inside WebView, back button, the real purchase flow, R8 build, the GitHub workflow (never executed), Android 16 tablet behaviour. All of that is the first hour of testing on a real phone via the internal track.
